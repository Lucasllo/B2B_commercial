<objective>
Levantar o esqueleto de build do repositório e entregar a **fatia vertical mais fina que prova a
arquitetura inteira**: um usuário real (o SELLER_ADMIN semeado no banco por uma migração Flyway)
faz login no auth-service, recebe um JWT RS256 assinado com uma chave gerada no startup, e usa
esse token para acessar um recurso protegido — tudo verificado contra um PostgreSQL real subido
por Testcontainers.

Purpose: este é o tracer do projeto. Ele atravessa build → Flyway → PostgreSQL → JPA → Spring
Security → HTTP numa única passada, de modo que qualquer beco sem saída arquitetural (versões
incompatíveis de Spring Cloud, wiring do `NimbusJwtEncoder`, configuração de schema do Flyway)
apareça agora, depois de um commit, e não depois de dez. O `auth-service` produzido aqui vira o
**analog canônico** que os quatro serviços das Fases 2 a 6 vão espelhar (estrutura de pacotes,
`SecurityConfig`, layout do Flyway, classe base de Testcontainers) — a estrutura precisa nascer
certa porque ela se propaga.

Nota sobre o número de arquivos: a Task 2 toca 19 arquivos. Isso não é uma tarefa
multi-subsistema disfarçada — é a granularidade normal do Java/Spring, onde um DTO é um `record`
de três linhas e um repositório é uma interface de uma linha. O conteúdo somado é uma única
fatia de login.

Output: reactor Maven com wrapper commitado, dois módulos empacotáveis, o schema `auth` no
Postgres, o SELLER_ADMIN semeado, o endpoint de login emitindo JWT verificável e a suíte de
testes de integração que prova tudo isso.
</objective>

    **Emissão de JWT (D-02).** `JwtIssuerConfig` é uma `@Configuration` que gera um par de
